### Zwift

Quellprüfung:

- [zwift-client](https://github.com/sandeepvasani/zwift-client/tree/02effd3d08c9c14b2d739ce2be6e1a133f3b430d), letzter Commit 2018-04-09. Relevant: `zwift/auth.py`, `request.py`, `profile.py`, `activity.py`.

- Kein Referenzcode als Abhängigkeit übernommen; eigene Swift-Implementierung. Öffentliche Client-ID `Zwift_Mobile_Link`, kein fremdes Client-Secret. Dieser Client ist kein eigener, von Zwift freigegebener OAuth-Client.

Am 2026-10-20 tatsächlich ohne Zugangsdaten abgefragt:

| Anfrage | Ergebnis |
| --- | --- |
| `GET https://secure.zwift.com/auth/realms/zwift/.well-known/openid-configuration` | HTTP 200; veröffentlicht OIDC-Token-/Authorize-URL, Password Grant und S256-Unterstützung auf Realm-Ebene |
| `POST https://secure.zwift.com/auth/realms/zwift/tokens/access/codes`, nur belegte Client-ID und Grant, keine Kontodaten | HTTP 401, `invalid_request`, fehlender Benutzername |
| `GET https://us-or-rly101.zwift.com/api/profiles/me`, ohne Token | HTTP 401 |

Die Realm-Metadaten beweisen weder die Zulässigkeit eines bestimmten Grants für diese Client-ID noch eine Redirect-Freigabe für FITgap. Der Prüfclient verwendet deshalb den im Referenzcode belegten Tokenpfad, keine erfundene Redirect- oder Client-Konfiguration.

Belegte, noch nicht authentifiziert geprüfte Routen: `/api/profiles/me`, `/api/profiles/{id}/activities/?start={offset}&limit={limit}`. FIT-URL aus `fitFileBucket` und `fitFileKey` gemäß Referenz: `https://{bucket}.s3.amazonaws.com/{key}`. Keine Zugangstokens an den Speicherhost; Weiterleitungen werden abgelehnt. API-Änderungen, Direktzugriffsverbote, MFA und Änderungen des Speicherzugriffs bleiben mögliche Grenzen. Bei einem echten Fehler an der betroffenen Stufe stoppen und den konkreten Befund auswerten.

**Kontostand:** Keine Anmeldung, keine echte Aktivitätsliste und keine echte FIT geprüft. Zugangsdaten lagen nicht vor. Nächster Schritt: Nutzer führt den gebauten Prüfclient lokal mit eigenem Konto aus. Keine Funktionszusage für die inoffizielle Integration; keine stabile öffentliche Zwift-API für FITgap nachgewiesen.

### Wahoo

Quelle: [offizielle Cloud-API-Dokumentation](https://cloud-api.wahooligan.com/), am Prüftag gelesen, Changelog bis 2026-10-09.

Dokumentiert: öffentliche Apps mit `Confidential? = No`, PKCE/S256; `https://api.wahooligan.com/oauth/authorize` und `/oauth/token`. Minimal benötigte Scopes: `user_read workouts_read` (`user_read` verhindert dokumentierten 403). Listenroute `/v1/workouts` mit `page`/`per_page`; FIT-Link in `workout_summary.file.url`, gegebenenfalls Detailabruf `/v1/workouts/{id}`. Dokumentation garantiert keine Byteidentität mit einer Geräte-Ursprungsdatei; am echten Export vergleichen.

Sandbox: 25 Requests/5 Minuten, 100/Stunde, 250/Tag. Authentifizierung, Refresh und Dateidownload zählen nicht mit. Produktion erfordert Wahoo-Review; keine Freigabe beantragt. Fremdanbieter-Workouts werden ausdrücklich nicht über diese API geteilt. Wahoo ersetzt daher keinen direkten Zwift-Zugriff.

**Blocker:** Nutzer bestätigt: noch keine eigene Developer-App registriert. Keine OAuth- oder Kontoabfrage vorgenommen. Nutzer muss im [Developer-Portal](https://developers.wahooligan.com/applications) eine Sandbox-App anlegen: Name `FITgap`, öffentlich (`Confidential? = No`), Scopes `user_read workouts_read`. Vorgesehene Redirect-URI `fitgap://oauth/wahoo` muss vom Portal akzeptiert werden; noch kein Laufzeitnachweis. Kein Secret in eine native App übernehmen.
